# Feature Specification: Engineering Communication Assistant

**Feature Branch**: `002-engineering-communication-assistant`

**Created**: 2026-08-09

**Status**: Draft

**Input**: User description: "Build an AI-powered Engineering Communication Assistant that transforms analysis findings into structured conversations with engineers. It must never act as a performance monitor. Purpose: keep Jira aligned with reality, collect missing information, surface blockers early. MVP scope: analyze previous sprint findings, detect whether communication is required, generate contextual Slack messages, present follow-ups for manager approval, send only approved messages, monitor engineer replies, summarize responses back to the manager, no autonomous messaging in MVP. Manager approval workflow: for every follow-up include Jira issue, engineer, reason, draft message, confidence level, suggested urgency. Actions: Approve, Edit, Ignore, Approve All. Slack experience: manager runs `/followups <squad>` — assistant presents follow-ups, waits for approval, sends approved private messages, monitors replies, returns concise summaries. Builds on existing EngPilot (001-em-copilot)."

## Clarifications

### Session 2026-08-09

The following clarifications were resolved by the Spec Kit autopilot using constitution-aligned defaults, the feature description, and consistency with feature 001 (`001-em-copilot`). Each answer is recorded here and integrated into the sections listed. See `autopilot-assumptions.md` for the confidence rating of each assumption.

- Q: What is the concrete Slack trigger surface that receives `/followups <squad>` and manager approval actions? → A: A Cursor Automation `slackTrigger` listening on the manager's configured Slack destination (the same on-demand mechanism as feature 001, per feature 001's plan-phase decision). The `/followups <squad>` syntax is illustrative; the actual invocation is a Slack message whose text is parsed by the automation using the same intent/squad-resolution rules from feature 001 (FR-011: case-insensitive, whitespace-collapsed, tolerant of trailing punctuation), with `followups` (or `follow-ups`) as the primary intent keyword and the trailing token(s) as the squad identifier. Interactive Slack Block Kit buttons and any interactivity-URL callbacks are prohibited (they require a hosted listener, which violates Constitution Principle I — Cursor-Only Runtime). Manager actions (Approve, Edit, Ignore, Approve All, status) MUST arrive as follow-up Slack messages on the same `slackTrigger` in the same manager destination. (Integrated into FR-006 and FR-019.)
- Q: How is the reply-monitoring window bounded? → A: The reply-monitoring window MUST be bounded by the Cursor Cloud Agent run associated with the cycle invocation. Within that run, the manager MAY invoke a status check (a follow-up Slack message parsed as a `status` intent for the squad, e.g., "status storefront" or "/followups status storefront") to force the assistant to (re-)read replies and post an updated per-engineer/per-issue summary. When the Cursor run terminates (for any reason), the window closes; a subsequent `/followups <squad>` invocation MUST start a fresh cycle with empty in-cycle context (FR-032). No background listener, no long-lived agent, and no reply-state persistence across cycles. (Integrated into FR-027 and Assumptions.)
- Q: What is the "possibly stale" freshness threshold for the consumed EngPilot analysis, and is it configurable? → A: 24 hours by default. The threshold MUST be configurable per deployment via the same feature-001-owned configuration file (recommended key: `communicationAssistant.analysisFreshnessHours`, integer > 0). When the analysis is older than the configured threshold, the cycle preview MUST flag the analysis as `possibly stale` and disclose the analysis timestamp. Cycles are never blocked on staleness — the manager decides whether to re-run analysis before approving. (Integrated into FR-009.)
- Q: What are the exact semantics of the 3-level Confidence and Urgency scales? → A: Both scales are 3-level ordinal (`Low` / `Medium` / `High`); numeric percentages are prohibited (Assumptions, feature 001 FR-015). **Confidence** (already defined in FR-017): `High` = deterministic-rule finding with unambiguous Jira signal; `Medium` = contextual AI-derived finding with corroborating deterministic signal; `Low` = contextual AI-derived finding without corroborating deterministic signal. **Urgency**: `High` = the underlying signal (blocker on P0/P1-tier sprint work, imminent slip against sprint end, or unowned dependency on a P0/P1-tier item) is likely to affect the sprint outcome if the conversation is delayed past today; `Medium` = the signal warrants same-day-or-next-day manager triage (e.g., stale in-progress item on non-critical work, missing estimate on a mid-priority item, unclear Jira status on active work); `Low` = routine progress inquiry or hygiene follow-up with plenty of sprint time remaining and no adjacent risk signal. Urgency is a triage signal to the manager, NOT a pressure signal in the drafted message (FR-018). (Integrated into FR-017 and FR-018.)
- Q: How does the manager perform Approve, Edit, Ignore, and Approve All actions in Slack — via interactive buttons or text commands? → A: Text commands only (interactive Block Kit buttons are prohibited — see Q1 above). The cycle preview MUST number proposals starting at 1 within the cycle. The supported commands, parsed by the same Cursor Automation `slackTrigger` in the same manager destination as the invocation, are: `approve <n>` (approves proposal `<n>` in its current draft form); `approve <n1,n2,...>` (multiple individual approvals in one message); `edit <n>: <revised message text>` (records the edit; a subsequent `approve <n>` sends the revised text); `ignore <n>`; `approve all` (approves every proposal that is still `pending`, in its current draft form — matches FR-019); `status` (triggers reply summary — see Q2). Commands MUST be case-insensitive and whitespace-tolerant, consistent with feature 001 FR-011. Unknown or malformed commands MUST produce a helpful validation reply listing the supported forms and MUST NOT send any message. (Integrated into FR-019, FR-020, FR-021.)
- Q: What defines the boundary of a single follow-up cycle (when it starts, when it ends, and how concurrent invocations are handled)? → A: A follow-up cycle **starts** on a valid `/followups <squad>` invocation received by the Cursor Automation `slackTrigger` for a configured squad. It **exists** only for the duration of the associated Cursor Cloud Agent run and its in-cycle context (FR-030) is scoped to that run only. It **ends** when that Cursor run terminates for any reason — successful completion after a cycle-closing manager action (`done`, `close cycle`, or no further pending proposals and no outstanding reply-summary request), timeout, run failure, or explicit termination. **Concurrent cycles** are independent: two `/followups <squad>` invocations (for the same squad or different squads) MUST NOT merge or coalesce, consistent with feature 001's independent-runs rule (FR-018 in 001). A subsequent `/followups <squad>` invocation always starts a fresh cycle with an empty in-cycle context (FR-032). (Integrated into new FR-043 and FR-032.)
- Q: Is there a maximum number of proposals per cycle, consistent with feature 001's Slack-length caps? → A: Yes. The cycle preview MUST cap at **10 proposals per cycle**, matching feature 001's follow-up-drafts cap (001 FR-022). When the underlying analysis yields more than 10 candidate proposals, the top 10 by (Urgency, Confidence) are shown and the overflow is disclosed as a single trailing "N additional proposals not shown" line under the "data limitations" bullet list (FR-040), so the manager knows what was intentionally omitted. This cap is configurable via the same feature-001-owned configuration file (recommended key: `communicationAssistant.maxProposalsPerCycle`, integer > 0). (Integrated into FR-019 and FR-040.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Manager-Approved Follow-Up Cycle in Slack (Priority: P1)

The engineering manager invokes the assistant in Slack for one configured squad (for example `/followups storefront`). The assistant reuses the most recent EngPilot squad analysis (from feature 001) as its evidence base, detects which findings actually warrant a conversation with a specific engineer, and produces a structured list of follow-up proposals. Each proposal presents the Jira issue key, the engineer to be contacted, the reason (chosen from a documented set: progress update, blocker clarification, estimate reminder, Jira status reminder, dependency follow-up, or sprint risk clarification), a copy-ready draft message written in polite, professional, non-accusatory language, a confidence level, and a suggested urgency. The manager can Approve, Edit, or Ignore each proposal individually, or use Approve All. Only proposals the manager explicitly approves (in original or edited form) are delivered as private direct messages to the mapped engineer's Slack user. The assistant confirms delivery outcomes back to the manager in the same Slack context.

**Why this priority**: This is the entire manager-facing loop for the feature and the shortest useful end-to-end path. Without it, no follow-up is ever sent and the assistant cannot deliver on its purpose (keeping Jira aligned with reality and surfacing blockers). It also establishes the manager-approval boundary that is a constitutional requirement (Human-Controlled Communication) — every later slice depends on the guarantee that nothing is sent without approval.

**Independent Test**: Fully testable by seeding an EngPilot analysis fixture for one configured squad that contains a mix of findings (stale in-progress item, blocked item without dependency owner, in-progress item without estimate, sprint-risk item with ambiguous status, cross-squad dependency), invoking the assistant with `/followups <squad>`, verifying that (a) the returned Slack message lists proposals with all required fields (issue, engineer, reason, draft, confidence, urgency) in neutral language, (b) each proposal cites the specific finding from the analysis as evidence, (c) actions Approve / Edit / Ignore / Approve All are presented per proposal and in bulk, (d) only approved proposals produce a Slack direct message to the engineer's mapped Slack user (verified against a Slack fixture), and (e) unapproved and ignored proposals produce zero outbound Slack messages.

**Acceptance Scenarios**:

1. **Given** a recent EngPilot analysis for the `Storefront` squad shows two stale in-progress items assigned to two different engineers, one blocked item with no dependency owner, and one in-progress item missing an estimate, **When** the manager sends `/followups storefront` in the configured Slack destination, **Then** the assistant replies with a follow-up cycle preview containing exactly four numbered proposals (starting at 1) — one per underlying finding — each showing the Jira issue key, the engineer to be contacted, the reason type (progress update, progress update, blocker clarification, estimate reminder), a draft message, a confidence level, and a suggested urgency, and the preview enumerates the supported per-proposal text commands (`approve <n>`, `edit <n>: <text>`, `ignore <n>`) and the cycle-level `approve all` command.
2. **Given** the same follow-up cycle preview from scenario 1, **When** the manager sends `approve 1,2` (approves proposals 1 and 2 as drafted), `edit 3: <revised text>` followed by `approve 3` (edits and approves proposal 3), and `ignore 4` (ignores the fourth) — all as follow-up messages on the same Slack trigger — **Then** the assistant sends exactly three Slack direct messages (two using the original draft and one using the manager-edited text) to the correctly mapped Slack user for each proposal's engineer, and sends zero messages for the ignored proposal.
3. **Given** the manager sends `approve all` on a cycle containing five proposals, **When** the assistant processes the bulk approval, **Then** all five approved messages are sent as private direct messages to the mapped Slack users, and the assistant returns a per-proposal delivery status back to the manager (`sent` or `failed with reason`) without exposing any secret or credential value.
4. **Given** the assistant analyzes findings for a squad and none of the findings warrant a conversation (for example, everything is On Track, or hygiene findings do not map to a supported follow-up reason type), **When** the assistant produces its output, **Then** it explicitly states that no follow-ups are required for this cycle and returns zero proposals, and does not invent proposals or send any messages.
5. **Given** a proposal targets an engineer for whom no Slack user mapping exists in configuration, **When** the manager approves that proposal, **Then** the assistant does NOT attempt to send a message, marks that proposal as `skipped: missing recipient mapping`, and discloses the skip in the delivery summary — without failing the cycle for other engineers.
6. **Given** the manager sends `/followups <unknown-squad-name>`, **When** the squad name cannot be resolved against configured display names or aliases, **Then** the assistant replies with a validation message listing the configured squads and their aliases, and produces zero proposals and zero messages.
7. **Given** no EngPilot analysis output is available for the requested squad (analysis has never been run or the last run failed), **When** the manager invokes the follow-up cycle, **Then** the assistant does NOT fabricate findings, does NOT produce proposals, and instead returns a message asking the manager to run an EngPilot analysis first, naming the exact command or trigger to do so.

### User Story 2 - Reply Monitoring and Manager Summary (Priority: P2)

After the assistant has delivered a set of approved follow-up messages, engineers reply to their direct messages. Within the same follow-up cycle, the assistant reads those replies, extracts the useful signal from each (current progress, an ETA, a named blocker, a status alignment note, a dependency owner, or "no update yet"), and returns a concise summary to the manager. The summary is grouped by engineer, references the Jira issue key associated with each reply, highlights blocker signals detected in the reply, marks proposals that require manager attention (for example, a reply indicating an unresolved external blocker, a slipping estimate, or an ambiguous status), and — for each item — recommends one of: `no further follow-up needed`, `another follow-up suggested (draft on request)`, or `manager attention recommended`. The assistant does NOT autonomously send any additional messages based on replies; any follow-up prompted by a reply must go through the same manager-approval workflow as the original cycle.

**Why this priority**: This is the outcome the manager actually wants — replies distilled into actionable signal without the manager reading every DM. It depends on P1 having sent approved messages, so it comes second. It also enforces the constitutional guarantee that reply reading never becomes reply reacting: even a reply that clearly indicates a blocker never triggers autonomous action.

**Independent Test**: Fully testable by driving a fixture in which three approved follow-up messages have been "sent" to three engineers and each has a fixture reply (one containing a clear blocker phrase and an ETA slip, one confirming current progress with an ETA, one saying "not started yet"), invoking the reply-summary path, and verifying that (a) the summary references each engineer and each Jira issue key, (b) the blocker reply is flagged with `manager attention recommended`, (c) the progress-confirmation reply is marked `no further follow-up needed`, (d) the "not started yet" reply is marked `another follow-up suggested (draft on request)` with no draft actually generated until the manager asks for it, and (e) no outbound Slack message is emitted to any engineer as a side effect of processing the replies.

**Acceptance Scenarios**:

1. **Given** three approved follow-up messages have been delivered in the current cycle and Slack fixtures indicate that all three engineers have replied, **When** the assistant produces the reply summary, **Then** it returns a per-engineer summary grouped by recipient, each including the Jira issue key, a short extraction of the reply content (progress, blocker, ETA, status alignment, or `no update yet`), and a per-item recommendation from the fixed set (`no further follow-up needed`, `another follow-up suggested (draft on request)`, `manager attention recommended`).
2. **Given** a reply contains a clear blocker signal (for example, an unresolved external dependency, a named third-party outage, or a firm statement that work cannot proceed), **When** the assistant processes that reply, **Then** the item is marked `manager attention recommended` and the summary states the specific blocker signal detected, so the manager can decide whether to intervene.
3. **Given** a reply contains no useful signal (for example, `ok`, `thanks`, an emoji only, or empty text), **When** the assistant processes that reply, **Then** the item is marked `no further follow-up needed` OR `another follow-up suggested (draft on request)` based on whether the original question was answered, and the assistant does NOT infer a blocker or delivery risk that the reply does not support.
4. **Given** one or more engineers have not replied within the reply-monitoring window for the current cycle, **When** the assistant produces the reply summary, **Then** those items are marked `no reply yet within cycle window` and the assistant does NOT send any autonomous reminder to those engineers.
5. **Given** the assistant recommends `another follow-up suggested (draft on request)` for an item, **When** the manager sends `draft another <n>` (where `<n>` is the proposal index from the reply summary) as a follow-up message in the same cycle, **Then** the assistant generates a new proposal that flows through the same Approve / Edit / Ignore workflow as P1, and only then can any additional message be sent — the reply itself never causes a message to be sent.

### User Story 3 - Cycle Context Awareness (Priority: P3)

Within a single follow-up cycle, the assistant remembers which questions it has already asked which engineers, and — if the manager triggers a second round of proposals inside the same cycle (for example after seeing replies) — the assistant does NOT ask the same engineer the same question about the same Jira issue again. When it does propose a new follow-up on the same issue for the same engineer, the draft explicitly references the engineer's previous answer from earlier in the same cycle (for example, "Thanks for the update — you mentioned the API contract is still pending; do you have a revised ETA?"). This context is scoped to the current cycle only; the assistant does NOT maintain any long-term memory of past cycles across separate Cursor runs, in line with the constitution's no-persistent-store constraint.

**Why this priority**: This directly protects engineer trust (the top-line success criterion "preserve engineer trust") by preventing the assistant from feeling like a chatbot that ignores previous answers. It is P3 because it enhances P1 and P2 rather than being required for the minimal loop — even without this, the manager can still run a working approve-and-send cycle and receive reply summaries.

**Independent Test**: Fully testable by driving a cycle in which the manager approves an initial follow-up to engineer A about issue `STORE-42` ("current progress?"), simulating a reply from engineer A ("API contract still pending, no ETA"), then invoking the "draft another follow-up on request" path from P2 for the same engineer and issue, and verifying that (a) the new proposal does NOT repeat the "current progress?" question verbatim, (b) the new draft references the previous answer (e.g., mentions "API contract is still pending" or the substance of the previous reply), and (c) starting a completely new cycle (a fresh `/followups <squad>` invocation) does NOT carry state from the previous cycle.

**Acceptance Scenarios**:

1. **Given** the current cycle already asked engineer A about issue `STORE-42` for a progress update and engineer A replied "waiting on the API contract review — no ETA yet", **When** the manager asks for another follow-up on the same engineer and issue within the same cycle, **Then** the new proposal's draft references the previous answer explicitly (for example, by acknowledging the API-contract dependency the engineer named) and does NOT repeat the exact same question ("current progress?") verbatim.
2. **Given** the current cycle already delivered two approved messages to engineer B about issues `PAY-11` and `PAY-14`, **When** a new proposal is drafted in the same cycle for engineer B about issue `PAY-11`, **Then** the assistant treats it as a continuation and references the prior message about `PAY-11`; **When** a new proposal is drafted in the same cycle for engineer B about a different issue `PAY-15`, **Then** the assistant treats it as a fresh conversation on the new issue with no forced back-reference.
3. **Given** a new `/followups <squad>` invocation begins after a previous cycle has ended, **When** the assistant produces its first set of proposals, **Then** it does NOT reference or assume the existence of any prior cycle's replies, questions, or approvals, because cycle context does not persist across separate cycles in the MVP.

### Edge Cases

- **No EngPilot analysis available for the squad**: The assistant refuses to fabricate findings and asks the manager to run an analysis first; it does not produce proposals from thin air.
- **Analysis is stale (older than a documented freshness threshold)**: The assistant proceeds but discloses the analysis timestamp so the manager can decide whether to re-run before approving messages.
- **Every finding is "no material concern"**: The assistant states that no follow-ups are required for this cycle and produces zero proposals.
- **A finding does not map to any supported follow-up reason type**: The finding is not converted into a proposal; it is disclosed in a "no proposal generated" note so the manager can see what was intentionally skipped.
- **Engineer has no Slack user mapping in configuration**: Any proposal targeting that engineer is preserved in the preview so the manager sees it, but on approval it is marked `skipped: missing recipient mapping` and no message is sent.
- **Slack DM delivery fails for one engineer** (rate-limited, blocked, or user deactivated): The failure is surfaced per proposal with a machine-readable reason; other approved messages in the cycle still deliver.
- **Manager ignores every proposal**: Zero messages are sent; the cycle closes cleanly with an "all proposals ignored" summary.
- **Manager edits a draft to include prohibited content** (blame, ranking, HR-style language): The assistant sends what the manager approved (the manager is the authority), but the assistant itself never composes such content in a generated draft; the assistant MAY warn the manager once before sending, but MUST NOT block a manager-approved message.
- **Engineer replies with off-topic, HR-related, or clearly private content**: The assistant does NOT act on that content; it summarizes only the on-topic signal (or marks the reply `no on-topic content extracted`), does NOT quote sensitive personal content back into the manager summary verbatim beyond a neutral acknowledgement, and does NOT autonomously escalate to any HR-adjacent recipient.
- **Engineer never replies within the reply-monitoring window**: Item marked `no reply yet within cycle window`; no automatic reminder is sent.
- **Squad name is unknown or ambiguous**: The assistant returns a validation message listing configured squads and their aliases; zero proposals produced.
- **Manager invokes `/followups <squad>` twice in quick succession**: Each invocation starts an independent cycle; the assistant does NOT merge or coalesce cycles.
- **Two proposals in the same cycle would ask the same engineer the same question about the same issue**: The assistant de-duplicates within the cycle before presenting proposals to the manager.
- **The manager approves a proposal but then loses the Slack context** (e.g., Slack app closes) before the assistant confirms delivery: The delivery result is still recorded in the assistant's run output; on the next manager invocation the assistant does NOT re-send anything automatically.
- **Configuration is missing the manager's Slack destination or the engineer→Slack user mapping section entirely**: The assistant refuses to run the follow-up cycle and returns an actionable configuration error naming the missing field.
- **A finding references a Jira issue key the assistant cannot resolve** (deleted, moved, or permission-denied): The corresponding proposal is not generated; the skip is disclosed under a "data limitations" note.

## Requirements *(mandatory)*

### Functional Requirements

**Runtime and delivery boundary**

- **FR-001**: The system MUST execute all follow-up cycle logic (finding-to-proposal conversion, draft generation, manager-approval intake, Slack delivery, reply summarization) through Cursor capabilities only (Cursor Cloud Agents, Cursor Automations, and Cursor-supported Slack triggers), consistent with feature 001. It MUST NOT introduce a hosted backend, web server, VM, container service, serverless function, queue, database, or independently hosted scheduler.
- **FR-002**: The system MUST integrate with only Jira (read-only) and Slack as external systems; no other external services are permitted in the MVP.
- **FR-003**: The system MUST NOT send any Slack message to a team member without explicit manager approval for that specific proposal (Approve on an individual proposal or Approve All on the cycle). Autonomous or scheduled sending of engineer-facing messages is prohibited in the MVP.
- **FR-004**: The system MUST NOT perform any Jira write operation (no comments, transitions, estimates, assignments, sprint scope changes, or field updates) as a result of a follow-up cycle or of any engineer reply.
- **FR-005**: The system MUST NOT persist cycle state, proposals, approvals, delivered messages, or replies in any long-term store outside of what Cursor provides for its execution runs. Cycle context (see FR-030) exists only within the current cycle's execution scope.

**Trigger, squad resolution, and analysis input**

- **FR-006**: The system MUST accept a manager-initiated Slack request whose text names the "follow-ups" intent (keywords `followups` or `follow-ups`) and one squad by display name or configured alias (illustrated as `/followups <squad>`). The trigger surface MUST be a Cursor Automation `slackTrigger` listening on the manager's configured Slack destination — the same on-demand mechanism as feature 001 (see feature 001 FR-006 and its plan-phase choice of `slackTrigger`). The request MUST originate from the manager's configured Slack destination or from a Slack context authorized by configuration. Interactive Slack Block Kit buttons and any Slack interactivity-URL callbacks are prohibited (they require a hosted listener endpoint, which violates Constitution Principle I — Cursor-Only Runtime). All manager actions on a cycle (see FR-019) MUST arrive as follow-up Slack messages on the same `slackTrigger` in the same manager destination.
- **FR-007**: Squad name resolution MUST reuse the same rules established in feature 001 (FR-010): case-insensitive, whitespace-collapsed, tolerant of trailing punctuation, exact-match against a configured squad's display name or alias; no fuzzy scoring. Unknown or ambiguous squad names MUST result in a validation reply listing the configured squads and aliases, and zero proposals.
- **FR-008**: The system MUST use the most recent successful EngPilot squad analysis (from feature 001) for the requested squad as the sole evidence base for finding-to-proposal conversion. When no EngPilot analysis is available for that squad, the system MUST return a message asking the manager to run an EngPilot analysis first, MUST NOT fabricate findings, and MUST produce zero proposals.
- **FR-009**: The system MUST disclose the timestamp of the EngPilot analysis it used, so the manager can decide whether to re-run analysis before approving messages. If the analysis is older than a configured freshness threshold (default: **24 hours**), the system MUST flag the analysis as `possibly stale` in the cycle preview. The threshold MUST be configurable per deployment (recommended key: `communicationAssistant.analysisFreshnessHours`, integer > 0). Staleness MUST NOT block a cycle from running; the disclosure is informational so the manager can choose to re-run analysis before approving messages.

**Detection: which findings require communication**

- **FR-010**: The system MUST determine, per finding in the EngPilot analysis, whether that finding warrants a conversation with a specific engineer. Only findings that (a) implicate a specific engineer as the appropriate recipient and (b) map to a supported follow-up reason type (see FR-011) are eligible to become proposals.
- **FR-011**: Supported follow-up reason types in the MVP MUST be exactly this set, and each proposal MUST be tagged with exactly one of them: `progress-update`, `blocker-clarification`, `estimate-reminder`, `jira-status-reminder`, `dependency-follow-up`, `sprint-risk-clarification`. Findings that do not map to any of these reason types MUST NOT become proposals; the skip MUST be disclosed under a "no proposal generated" note in the cycle preview.
- **FR-012**: Each proposal MUST cite the specific EngPilot finding (with its Jira evidence — issue key, status, age, blocker/dependency signal, estimate presence, or sprint timing — carried through from feature 001) that justifies the proposal. Proposals without concrete Jira evidence MUST NOT be generated (Evidence Before Conclusions, principle IV).
- **FR-013**: The system MUST determine the recipient of each proposal deterministically from the finding: for progress, blocker, estimate, and Jira-status reason types the recipient is the Jira issue's current assignee; for dependency follow-ups the recipient is the derivable dependency owner if identified in the analysis, otherwise the issue's assignee; for sprint-risk clarification the recipient is the issue's assignee. If no recipient can be derived from the analysis, no proposal is generated and the skip MUST be disclosed.

**Draft generation and language principles**

- **FR-014**: Every proposal MUST include exactly these fields in the cycle preview: (a) Jira issue key, (b) engineer (display name and, when the Slack user mapping exists, the mapped Slack user reference), (c) reason type from the FR-011 set, (d) draft message text, (e) confidence level (`Low` / `Medium` / `High`), (f) suggested urgency (`Low` / `Medium` / `High`).
- **FR-015**: Draft messages MUST be composed in polite, professional, non-accusatory language, MUST use open-ended questions where information is being requested, MUST include a short one-sentence explanation of why the question is being asked (referencing the observation, not judgment), MUST offer support rather than pressure (for example an explicit "let me know if I can help unblock something"), and MUST NOT use blaming, ranking, performance-evaluative, or urgency-manipulative phrasing.
- **FR-016**: Draft messages MUST NOT include productivity scores, ticket counts framed as performance, comparisons between engineers, or any language that could be read as an HR signal, disciplinary signal, or performance rating.
- **FR-017**: The confidence level of each proposal MUST reflect the strength of the underlying evidence (deterministic-rule finding with unambiguous Jira signal → `High`; contextual AI-derived finding with corroborating deterministic signal → `Medium`; contextual AI-derived finding without corroborating deterministic signal → `Low`). Confidence MUST NOT be presented as a numeric percentage.
- **FR-018**: The suggested urgency of each proposal MUST be one of `Low` / `Medium` / `High` and MUST reflect the delivery impact and timing of the underlying finding:
  - `High` — the signal (e.g., blocker on P0/P1-tier sprint work, imminent slip against sprint end, unowned dependency on a P0/P1-tier item) is likely to affect the sprint outcome if the conversation is delayed past today.
  - `Medium` — the signal warrants same-day-or-next-day manager triage (e.g., stale in-progress item on non-critical work, missing estimate on a mid-priority item, unclear Jira status on active work with material sprint time remaining).
  - `Low` — routine progress inquiry or hygiene follow-up with plenty of sprint time remaining and no adjacent risk signal.
  Urgency MUST NOT be manipulated to pressure the engineer; the drafted message MUST NOT reproduce the urgency label verbatim to the engineer. Urgency is a triage signal to the manager only.

**Manager approval workflow**

- **FR-019**: The cycle preview presented to the manager MUST number proposals starting at 1 within the cycle and MUST cap the preview at **10 proposals per cycle** (matching feature 001 FR-022; configurable via `communicationAssistant.maxProposalsPerCycle`). When more than 10 candidate proposals exist, the top 10 by (Urgency, Confidence) MUST be shown and the overflow disclosed under the "data limitations" bullet list (FR-040) as a single "N additional proposals not shown" line. The preview MUST offer exactly these actions per proposal, delivered as follow-up Slack messages on the same Cursor Automation `slackTrigger` in the same manager destination (Slack Block Kit buttons and interactivity-URL callbacks are prohibited per FR-006):
  - `approve <n>` — approves proposal `<n>` in its current draft form; multiple comma-separated indexes MAY be sent in one message (e.g., `approve 1,3,4`).
  - `edit <n>: <revised message text>` — records the revised text on proposal `<n>`; a subsequent `approve <n>` sends the revised text.
  - `ignore <n>` — marks proposal `<n>` as ignored; no message is sent.
  - `approve all` — cycle-level action; approves every proposal still in `pending` status in its current draft form. No other bulk actions (e.g., "ignore all", "send now") are in scope for the MVP.
  - `status` — triggers the reply-summary path (FR-027) for already-delivered proposals in this cycle.
  - `draft another <n>` — after a reply summary marks proposal `<n>` as `another follow-up suggested (draft on request)`, generates a new in-cycle proposal for the same (engineer, issue) pair that references the captured reply (FR-030) and flows through the same Approve / Edit / Ignore workflow; MUST NOT send any message until the manager approves the new proposal.
  - `done` or `close cycle` — closes the cycle (see FR-043).
  Commands MUST be case-insensitive and whitespace-tolerant, consistent with feature 001 FR-011. Unknown or malformed commands MUST produce a helpful validation reply listing the supported forms and MUST NOT send any message.
- **FR-020**: The assistant MUST NOT send any message for a proposal until the manager has issued an `approve <n>` on that specific proposal (either individually, in a comma-separated list, or via `approve all` covering that proposal). `ignore <n>` MUST result in zero messages for that proposal. Approval commands that reference an unknown proposal index MUST produce a validation reply and MUST NOT send any message.
- **FR-021**: When the manager sends `edit <n>: <revised message text>` and subsequently `approve <n>`, the assistant MUST send that revised text verbatim (subject to Slack rendering) as the direct message to the proposal's recipient. The assistant MAY, before sending, warn the manager once if the edited text contains language the assistant would not itself compose (blame, ranking, HR-style content), but MUST NOT refuse to send manager-approved content. Multiple `edit <n>: ...` messages on the same proposal MUST replace prior edits (last edit wins) until the proposal is approved, ignored, or the cycle ends.
- **FR-022**: The assistant MUST return a per-proposal delivery result to the manager after processing an approval batch: one of `sent`, `failed: <machine-readable reason>`, or `skipped: <reason>` (for example `skipped: missing recipient mapping`). Aggregate cycle-level status (for example `3 sent, 1 skipped, 1 failed`) MUST also be shown.

**Slack delivery**

- **FR-023**: Approved messages MUST be delivered as private Slack direct messages to the mapped Slack user for the proposal's engineer, using the engineer→Slack user mapping already configured in feature 001. The assistant MUST NOT deliver follow-ups in public channels, in group DMs, or to a manager-only channel.
- **FR-024**: If the engineer's Slack user mapping is missing from configuration, the assistant MUST NOT attempt a delivery, MUST mark the proposal `skipped: missing recipient mapping`, and MUST continue processing the remaining approved proposals in the cycle.
- **FR-025**: Slack delivery MUST use the least-privilege Slack bot token supplied via the same Cursor-supported secret mechanism as feature 001 (default variable name `SLACK_BOT_TOKEN`, overridable per configuration). The bot token MUST NEVER appear in any manager-facing message, log, or error.
- **FR-026**: For transient Slack failures (for example rate limiting), delivery MAY use bounded retries per the same policy as feature 001 (at most 3 attempts, approximately 1s / 2s / 4s exponential backoff, total wall-clock time under 60 seconds per proposal, authentication failures never retried). Unbounded retries are prohibited.

**Reply monitoring and manager summary**

- **FR-027**: After approved messages are sent within a cycle, the assistant MUST be able to read replies to those direct messages within the cycle's reply-monitoring window and produce a per-engineer, per-issue summary for the manager. The reply-monitoring window MUST be bounded by the **Cursor Cloud Agent run associated with the cycle invocation** (see FR-043 for the cycle boundary). Within that run, the manager MAY at any time send a `status` command (parsed by the same `slackTrigger` as the invocation, per FR-019) to trigger the assistant to (re-)read replies and post an updated per-engineer/per-issue reply summary in the same Slack destination. When the Cursor run terminates for any reason, the reply-monitoring window closes and no further replies are read for this cycle; a new `/followups <squad>` invocation MUST start a fresh cycle (FR-032) and MUST NOT resume reply reading for a prior cycle. The MVP MUST NOT retain reply state across cycles, MUST NOT run a background listener, and MUST NOT keep any long-lived agent alive between manager invocations.
- **FR-028**: The reply summary MUST group by engineer and, within each engineer, MUST reference the Jira issue key for each reply. For each reply, the summary MUST include: a short extraction of the on-topic content (progress, ETA, named blocker, status alignment, dependency owner, or `no on-topic content extracted`), any blocker signal detected, and a per-item recommendation drawn from exactly this set: `no further follow-up needed`, `another follow-up suggested (draft on request)`, `manager attention recommended`.
- **FR-029**: The assistant MUST NOT autonomously generate or send a follow-up message in response to a reply. When the recommendation is `another follow-up suggested (draft on request)` or the reply reveals a new blocker, any additional message MUST flow through the same Approve / Edit / Ignore / Approve All workflow as the original cycle. `manager attention recommended` MUST NOT trigger any outbound message on its own.

**Cycle context awareness**

- **FR-030**: Within a single follow-up cycle, the assistant MUST maintain in-cycle context of which engineer was asked which question about which Jira issue, and — if additional proposals are generated in the same cycle for the same (engineer, issue) pair — MUST NOT propose a draft that repeats the previous question verbatim, and MUST reference the substance of the engineer's previous answer if one was captured within the same cycle.
- **FR-031**: The assistant MUST de-duplicate proposals within a single cycle before presenting them to the manager: if two findings would produce the same (engineer, issue, reason-type) proposal, they MUST be consolidated into a single proposal citing all supporting evidence.
- **FR-032**: Cycle context MUST NOT persist across separate cycles; a new `/followups <squad>` invocation MUST start with an empty context and MUST NOT reference prior-cycle questions or replies.

**Constitutional guardrails (people-facing behavior)**

- **FR-033**: The assistant MUST NOT treat any part of this feature (findings analysis, draft generation, reply reading, summary composition) as a mechanism for performance monitoring. Story points, ticket counts, response latencies, or the tone of a reply MUST NOT be aggregated into any per-engineer performance signal, ranking, or score.
- **FR-034**: The assistant MUST NOT deliver public reminders about individual engineers' work (no channel posts naming an engineer's late or blocked work). All follow-up communication in this feature is private DM to the individual engineer.
- **FR-035**: The assistant MUST NOT make automatic Jira updates, sprint modifications, task reassignments, or scope changes as a result of a follow-up cycle or reply.
- **FR-036**: The assistant MUST NOT produce HR-adjacent recommendations (for example, escalation-to-HR, performance-improvement-plan suggestions, or disciplinary suggestions) as part of any manager summary. When a reply contains content that is clearly HR-adjacent, the assistant MUST NOT quote that content verbatim into the manager summary beyond a neutral acknowledgement and MUST NOT propose any follow-up message based on it.

**Failure handling, reliability, and disclosure**

- **FR-037**: When the required EngPilot analysis input is unavailable, the assistant MUST NOT run the cycle, MUST NOT fabricate findings, and MUST return an actionable message telling the manager to run the analysis first.
- **FR-038**: When per-proposal delivery fails, the failure MUST be surfaced with a machine-readable reason in the manager-facing cycle result, MUST NOT be re-attempted to a different Slack destination, and MUST NOT block the delivery of other approved proposals in the same cycle.
- **FR-039**: When reading replies fails (Slack permission missing, rate-limited beyond retry policy, or user unreachable), the affected replies MUST be marked in the reply summary as `unreadable: <reason>` and MUST NOT be silently omitted or fabricated.
- **FR-040**: Data limitations (missing engineer→Slack mapping, unreachable Jira issue, stale analysis, unread replies) MUST be disclosed as a dedicated bullet list at the end of the cycle preview or reply summary, following the same disclosure discipline established in feature 001 (FR-025).

**Testability**

- **FR-041**: The deterministic parts of this feature (finding-to-reason-type mapping in FR-011, recipient derivation in FR-013, confidence assignment in FR-017, urgency assignment in FR-018, in-cycle de-duplication in FR-031, and per-item recommendation classification in FR-028) MUST be independently exercisable against anonymized fixtures without live Jira or Slack access.
- **FR-042**: The AI-generated portions (draft message text, reply extraction, reply recommendation reasoning) MUST produce output validated against a structured shape before it is rendered to the manager or sent to any engineer, so that malformed or evidence-free AI output does not reach either audience (consistent with feature 001 FR-047).

**Cycle boundary**

- **FR-043**: A follow-up cycle MUST have a well-defined boundary:
  - **Start**: A cycle starts on a valid `/followups <squad>` invocation received by the Cursor Automation `slackTrigger` for a configured squad (FR-006, FR-007). Its in-cycle context (FR-030) is initialized empty.
  - **Lifetime**: The cycle exists only for the duration of the Cursor Cloud Agent run associated with its invocation. All cycle state — proposals, manager actions, delivery records, in-cycle context, reply-summary state — is held only for the lifetime of that run (FR-005).
  - **End**: The cycle ends when the associated Cursor Cloud Agent run terminates for any reason: successful completion (all proposals reached a terminal status — `sent`, `failed`, `skipped`, or `ignored` — and no outstanding reply-summary request remains, OR the manager sent `done` / `close cycle`), timeout, run failure, or explicit termination.
  - **Concurrency**: Concurrent cycles are independent. Two `/followups <squad>` invocations (for the same squad or different squads) MUST NOT merge or coalesce, consistent with feature 001 FR-018's independent-runs rule. Each invocation starts a fresh cycle with empty in-cycle context (FR-032).

### Key Entities *(include if feature involves data)*

- **Follow-Up Cycle**: A single manager-initiated invocation of the follow-up workflow for one squad. Has a squad reference, the timestamp of the EngPilot analysis it consumed, an in-cycle context (see below), a list of Proposals, and — after manager action — a list of delivery results and (optionally) a Reply Summary. Cycles do not persist across separate invocations.
- **Follow-Up Proposal**: A single draft-in-preview item. Has a Jira issue key, a recipient (engineer display name + optional mapped Slack user reference), a reason type from the fixed FR-011 set, a draft message text, a confidence level (`Low`/`Medium`/`High`), a suggested urgency (`Low`/`Medium`/`High`), a link to the underlying EngPilot finding(s) as evidence, and a status (`pending`, `approved`, `ignored`, `sent`, `failed`, `skipped`). Manager edits are held in `editedMessage` while status remains `pending` until approval (FR-021).
- **Manager Action**: A record of the manager's decision for one proposal or for the cycle. Has an action type (`Approve`, `Edit`, `Ignore`, `Approve All`), an optional edited message text (for `Edit`), and a timestamp.
- **Approved Message Delivery**: The record of what was actually sent to an engineer. Has the proposal reference, the final message text (original or edited), the recipient Slack user reference, a delivery status (`sent` / `failed` / `skipped`), and — on failure — a machine-readable reason.
- **Engineer Reply**: An engineer's direct-message response to a delivered follow-up. Has a delivery reference, the raw reply text (used internally, not re-quoted in the manager summary beyond a neutral extraction), an extracted on-topic content field, an optional detected blocker signal, and a per-item recommendation from the fixed FR-028 set.
- **Cycle Reply Summary**: The manager-facing summary produced from Engineer Replies. Grouped by engineer and, within each, by Jira issue key. Includes per-item extraction + recommendation and a "data limitations" bullet list when relevant.
- **In-Cycle Context**: The ephemeral state tracked within one cycle. Records which (engineer, issue) pairs have been asked which question and captures each engineer's on-topic answer within the cycle so that de-duplication (FR-031) and reference-to-previous-answer (FR-030) can happen. Discarded at cycle end.
- **Follow-Up Reason Type**: One of exactly six values — `progress-update`, `blocker-clarification`, `estimate-reminder`, `jira-status-reminder`, `dependency-follow-up`, `sprint-risk-clarification` — used to classify each proposal.
- **Data Limitation Notice**: A disclosure in the cycle preview or reply summary about something that could not be fully retrieved or acted on (missing recipient mapping, stale analysis, unreadable reply, unresolved Jira issue), following the same shape as feature 001's FR-025.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of generated follow-up proposals include all six required fields (Jira issue, engineer, reason type from the fixed set, draft message, confidence level, suggested urgency) and cite at least one supporting Jira evidence element carried from the EngPilot analysis, verified across the deterministic-rule test set and AI-output validation.
- **SC-002**: 0 outbound Slack messages are sent to engineers without an explicit manager `Approve` (individual or via `Approve All`) covering that specific proposal, verified across all fixture-driven test cycles.
- **SC-003**: 100% of approved messages are delivered as private direct messages to the mapped Slack user for the intended engineer; 0 messages are delivered to public channels, group DMs, or any recipient not derived from the configured engineer→Slack user mapping.
- **SC-004**: 100% of AI-generated draft messages pass a language-quality check for the constitutional principles (polite, non-accusatory, open-ended question, includes a one-sentence "why", offers support rather than pressure, contains no ranking / scoring / HR-adjacent language), verified against an anonymized fixture set of representative findings.
- **SC-005**: When no EngPilot analysis is available or no finding maps to a supported reason type, 100% of cycles return zero proposals and an explicit "no follow-ups required" (or "analysis required first") message, with zero fabricated proposals.
- **SC-006**: For every approved-and-delivered proposal, the assistant returns a per-item reply-summary entry (or an explicit `no reply yet within cycle window` marker) to the manager, referencing the correct Jira issue key and engineer, in 100% of test fixture cycles that include simulated replies.
- **SC-007**: 100% of engineer replies containing a configured blocker signal in fixtures are flagged `manager attention recommended` in the reply summary; 100% of replies containing no on-topic content are marked `no on-topic content extracted` (and never fabricated into a fake blocker).
- **SC-008**: 0 autonomous follow-up messages are generated or sent in response to any engineer reply; any additional follow-up flows through the same Approve / Edit / Ignore / Approve All workflow before delivery, in 100% of cases.
- **SC-009**: Within a single cycle, the assistant never proposes two drafts that ask the same engineer the same question about the same Jira issue (de-duplication), and any additional in-cycle proposal for the same (engineer, issue) pair references the substance of the engineer's previous in-cycle answer, in 100% of test fixture scenarios that exercise these paths.
- **SC-010**: 0 Jira write operations (comments, transitions, estimates, assignments, sprint scope changes, field updates) occur as a result of any follow-up cycle or engineer reply, verified against a read-only Jira permission fixture.
- **SC-011**: 100% of MVP paths for this feature (finding-to-proposal conversion, cycle preview, manager approval intake, Slack DM delivery, reply monitoring, cycle summary) run entirely on Cursor capabilities with no hosted backend, VM, container service, serverless function, queue, database, or independently hosted scheduler introduced.
- **SC-012**: 100% of generated proposals, delivered messages, and reply summaries are free of individual performance scoring, engineer ranking, productivity indices, ticket-count-as-performance framing, and HR-adjacent recommendations.
- **SC-013**: When the engineer→Slack user mapping is missing for a proposal's recipient, 100% of such proposals are marked `skipped: missing recipient mapping` and produce 0 delivery attempts, while other approved proposals in the same cycle still deliver normally.
- **SC-014**: Manager self-reports a reduction of at least 30 minutes of manual follow-up drafting-and-sending time per active sprint week (measured against the manager's self-reported baseline) after adopting the assistant, sustained over two consecutive sprints.
- **SC-015**: Manager self-reports improved Jira accuracy for the covered squad — specifically, a reduction in the count of open items with missing estimates, stale status, or unclear blockers at the end of each sprint compared to the sprint immediately before adoption — for at least two consecutive sprints. (Measured through the same EngPilot hygiene counts used in feature 001.)
- **SC-016**: Manager self-reports that blockers surfaced through this assistant's follow-ups (blockers named in engineer replies) reach the manager earlier than the manager's previous baseline for the same class of blocker, over two consecutive sprints.
- **SC-017**: Engineer feedback (collected out-of-band by the manager, not by the assistant) indicates that follow-up messages received are perceived as respectful and not surveillance-like, for at least the first two sprints of use; the assistant MUST NOT itself collect or aggregate this feedback into any per-engineer metric.

## Assumptions

- **EngPilot (feature 001) analysis is the sole evidence source for this feature**: This feature does not perform its own Jira analysis; it consumes the structured analysis output produced by feature 001 for the same squad. Any change to that output shape is a coordination point between features.
- **Engineer→Slack user mapping is supplied by feature 001's configuration**: The team-member-to-Slack-user mapping introduced in feature 001 (FR-007) is reused; this feature does not introduce its own mapping schema.
- **Manager's Slack destination is already configured**: The same manager Slack destination configured for feature 001 daily briefings (FR-008) is the authoritative source for who counts as the manager for follow-up cycle interactions.
- **Slack trigger surface is a Cursor Automation `slackTrigger`**: Per Clarifications Session 2026-08-09 and FR-006, the trigger is the same on-demand `slackTrigger` mechanism as feature 001. The `/followups <squad>` syntax is illustrative of the message text parsed by the automation; the actual invocation is a Slack message whose text is parsed for the `followups` (or `follow-ups`) intent and a squad identifier. Slack Block Kit interactive buttons and interactivity-URL callbacks are prohibited (Constitution I).
- **Reply-monitoring window is bounded by the Cursor Cloud Agent run**: Per Clarifications Session 2026-08-09 and FR-027 and FR-043, the reply-monitoring window is the current Cursor Cloud Agent run's lifetime. Within that run, the manager can send a `status` command to force a reply-summary refresh. Once the run ends, the window closes and no reply state persists across cycles (FR-005, FR-032). No background listener; no long-lived agent.
- **Confidence and urgency are 3-level ordinal values, not numeric percentages**: `Low` / `Medium` / `High` is a deliberate choice to avoid false precision, consistent with feature 001's rejection of numeric confidence in health classification (FR-015).
- **Draft messages are English (en-US) for the MVP**: Same localization boundary as feature 001; a future spec may add other languages.
- **The MVP covers one squad per `/followups` invocation**: Cross-squad simultaneous follow-up cycles are out of scope; the manager runs the command once per squad.
- **AI-generated draft text is always subject to manager approval before send**: The assistant never sends what it itself composed without a manager `Approve` action, even when confidence is `High`. Manager approval is the sole delivery gate.
- **Reply extraction is best-effort, not natural-language-inference-perfect**: The assistant is expected to extract clearly stated progress, ETAs, blocker names, and status alignment; it is NOT expected to perform sentiment analysis, personality inference, or engagement scoring, and MUST NOT do so.
- **Existing Cursor-supported secret mechanism from feature 001 is reused**: `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, `SLACK_BOT_TOKEN` (all overridable per configuration) are the same secret names carried over from feature 001 FR-041; no new secret categories are introduced.
- **Freshness threshold for "possibly stale" analysis is 24 hours by default**: This is the default flagging threshold for FR-009; the manager can always re-run analysis on demand. The exact threshold is configurable via `communicationAssistant.analysisFreshnessHours` (integer > 0). Staleness never blocks a cycle from running; the disclosure is informational.

## Out of Scope

The following capabilities are explicitly out of scope for this feature; introducing any of them would constitute either a separate specification or a constitutional exception.

- **Automatic or scheduled sending of engineer-facing follow-up messages** without manager approval. Autonomous messaging remains prohibited in the MVP (Human-Controlled Communication, principle V).
- **Performance scoring, engineer ranking, productivity indices, per-engineer response-latency metrics, and any per-engineer aggregation that could be read as a performance signal** — including any such aggregation over multiple cycles. (Manager Assistance, Not Employee Surveillance, principle III.)
- **Public reminders** about individual engineers' work (no channel posts naming engineers' late or blocked items). All follow-up communication is private DM only.
- **Automatic Jira updates or writes of any kind** (comments, transitions, estimates, assignments, sprint scope changes, field updates) triggered by this feature. (Safe, Read-First Integrations, principle VIII.)
- **Automatic sprint modifications** (adding, removing, or re-scoping issues in a sprint).
- **Automatic task reassignment** based on replies (for example, an engineer replies "I'm blocked, ask X" — the assistant surfaces this to the manager but MUST NOT reassign in Jira).
- **HR-adjacent recommendations**: escalation-to-HR suggestions, performance-improvement-plan drafts, disciplinary suggestions, coaching plans, or any other language that treats the feature as a management-of-people tool rather than a management-of-work tool.
- **Cross-cycle memory**: the assistant does NOT remember prior cycles' questions, replies, or approvals across separate `/followups <squad>` invocations. Long-lived follow-up conversation history is a future specification if ever needed.
- **A dashboard, web UI, or admin console** for reviewing follow-up cycles.
- **A queue, database, or independently hosted scheduler** to hold pending approvals or in-flight cycles.
- **Sending follow-up drafts to more than one recipient per proposal** (no group DMs, no cc'ing a lead alongside the assignee). One proposal targets exactly one engineer.
- **Escalation policies** (for example, "if no reply in 2 hours, DM the engineer's lead"). Any escalation is a manager decision in a separate cycle, not an assistant behavior.
- **Sentiment analysis, tone scoring, or personality inference** on engineer replies.
- **Follow-up cycles targeting more than one squad simultaneously** (the manager invokes once per squad).
- **A third or Nth squad** in configuration; the MVP remains at exactly two squads consistent with feature 001 FR-005.
- **Azure DevOps, GitHub, PR analysis, or calendar integration** as input signals or delivery channels; the feature stays on the Jira + Slack MVP surface.
