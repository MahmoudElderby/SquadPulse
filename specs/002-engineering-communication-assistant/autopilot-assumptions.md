# Autopilot Assumptions

**Feature**: `002-engineering-communication-assistant` — Engineering Communication Assistant (MVP)
**Session**: 2026-08-09
**Mode**: Full-auto (no user prompting)
**Basis for defaults**: `.specify/memory/constitution.md` (v1.0.0), the feature description, existing `spec.md` for this feature and `specs/001-em-copilot/spec.md` (and its `autopilot-assumptions.md`) for cross-feature consistency, and standard engineering practice where the constitution and specs are silent.

Each assumption below has been encoded into `spec.md` and is cross-referenced to the specific FR(s) it updated. See `spec.md` → `## Clarifications` → `### Session 2026-08-09` for the mirrored Q → A bullets.

| # | Topic | Question / Gap | Assumption chosen | Confidence |
|---|-------|----------------|-------------------|------------|
| 1 | Concrete Slack trigger surface | Spec (pre-clarify FR-006 and Assumptions) treated `/followups <squad>` as illustrative and deferred the actual trigger surface to plan. This left it ambiguous whether interactive Slack Block Kit buttons were permitted for manager actions. | Trigger surface is a **Cursor Automation `slackTrigger`** listening on the manager's configured Slack destination, matching feature 001's plan-phase choice (001 autopilot-assumptions #23). The `/followups <squad>` syntax is illustrative — the actual invocation is a Slack message whose text is parsed by the automation using feature 001's intent/squad-resolution rules (case-insensitive, whitespace-collapsed, tolerant of trailing punctuation) with `followups`/`follow-ups` as the primary intent keyword. **Slack Block Kit interactive buttons and any interactivity-URL callbacks are prohibited** — they require a hosted listener endpoint, which violates Constitution Principle I (Cursor-Only Runtime). All manager actions on a cycle arrive as follow-up Slack messages on the same `slackTrigger`. Encoded in FR-006, FR-019, and Assumptions. | high |
| 2 | Reply-monitoring window mechanism | Pre-clarify FR-027 explicitly deferred the window mechanism to plan ("for example, 'for the remaining duration of the current Cursor execution' or 'on manager-invoked `/followups status <squad>`'"). Left the boundary between "still monitoring replies" and "cycle closed" ambiguous. | The reply-monitoring window is bounded by the **Cursor Cloud Agent run associated with the cycle invocation** (see cycle boundary in FR-043). Within that run, the manager MAY send a `status` command (parsed by the same `slackTrigger`) to force the assistant to (re-)read replies and post an updated reply summary. When the Cursor run terminates for any reason, the window closes; a subsequent invocation starts a fresh cycle with empty in-cycle context (FR-032). No background listener, no long-lived agent, no reply-state persistence across cycles (FR-005). Encoded in FR-027, FR-043, and Assumptions. | med |
| 3 | Analysis freshness threshold | Pre-clarify FR-009 said "default: 24 hours" but did not confirm the value was configurable or specify the config key, and did not clarify whether staleness could block a cycle. | Default **24 hours**; MUST be configurable per deployment via `communicationAssistant.analysisFreshnessHours` (integer > 0). Staleness MUST NOT block a cycle from running — the disclosure is informational so the manager can decide to re-run analysis before approving. Encoded in FR-009 and Assumptions. | high |
| 4 | Confidence and urgency scale semantics | Pre-clarify FR-014/FR-017 defined 3-level ordinal confidence with rules; FR-018 defined urgency with only illustrative examples (`High` on P0/P1 blocker with little sprint time, `Low` on routine early-sprint). Explicit boundary conditions for `Medium` urgency and the crisp definition of "little sprint time" were missing. | Both scales are 3-level ordinal (`Low` / `Medium` / `High`); numeric percentages prohibited (Assumptions, 001 FR-015). **Confidence** unchanged from FR-017. **Urgency**: `High` = signal likely to affect sprint outcome if delayed past today; `Medium` = warrants same-day-or-next-day manager triage; `Low` = routine progress inquiry or hygiene follow-up with plenty of sprint time remaining. Urgency is a triage signal to the manager only; the drafted message MUST NOT reproduce the urgency label verbatim to the engineer. Encoded in FR-017, FR-018. | high |
| 5 | Manager approval actions in Slack (buttons vs text commands) | Pre-clarify FR-019 named the actions (`Approve`, `Edit`, `Ignore`, `Approve All`) but did not specify how they are delivered in Slack. Given Constitution Principle I (Cursor-Only Runtime) prohibits hosted listener endpoints, Block Kit interactive buttons are not viable. | **Text commands only**, delivered as follow-up Slack messages on the same Cursor Automation `slackTrigger` in the same manager destination. Cycle preview numbers proposals starting at 1. Supported commands (case-insensitive, whitespace-tolerant, per 001 FR-011): `approve <n>` (or comma-separated list), `edit <n>: <revised message text>`, `ignore <n>`, `approve all`, `status`, `done` / `close cycle`. Unknown commands produce a helpful validation reply and send no message. Encoded in FR-019, FR-020, FR-021. | high |
| 6 | Cycle boundary definition | Pre-clarify FR-005/FR-030/FR-032 established that cycle context does not persist across cycles, but there was no single clause defining when a cycle starts, when it ends, or how concurrent invocations are handled. | Cycle **starts** on a valid `/followups <squad>` invocation received by the `slackTrigger`. Cycle **exists** only for the lifetime of the associated Cursor Cloud Agent run. Cycle **ends** on run termination for any reason — successful completion (all proposals terminal AND no outstanding reply-summary request, OR manager sends `done` / `close cycle`), timeout, run failure, or explicit termination. **Concurrent** cycles are independent (consistent with 001 FR-018): two `/followups <squad>` invocations MUST NOT merge or coalesce; each starts a fresh in-cycle context (FR-032). Encoded in new FR-043 and FR-032. | med |
| 7 | Maximum proposals per cycle | Pre-clarify spec (FR-019 and elsewhere) did not cap proposal count per cycle, though feature 001 caps follow-up drafts at 10 per squad report (001 FR-022). Uncapped previews risk exceeding Slack length limits and overwhelming the manager. | **10 proposals per cycle maximum**, matching feature 001 FR-022. When more than 10 candidates exist, the top 10 by (Urgency, Confidence) are shown and the overflow is disclosed under the "data limitations" bullet list (FR-040) as a single "N additional proposals not shown" line. Cap is configurable via `communicationAssistant.maxProposalsPerCycle` (integer > 0). Encoded in FR-019 and FR-040 (by cross-reference). | high |

## Plan Phase Decisions (2026-08-09)

The following architectural choices were made during `/speckit-plan` and encoded in `plan.md`, `research.md`, `data-model.md`, and `contracts/`. Each extends clarify-phase assumptions where the spec deferred implementation mechanism to plan.

| # | Topic | Gap resolved in plan | Decision chosen | Confidence |
|---|-------|----------------------|-----------------|------------|
| 8 | EngPilot analysis input mechanism | Spec FR-008 requires "most recent successful EngPilot analysis" but feature 001 currently emits Slack Markdown only — no structured cross-run artifact. | Feature 001 writes a gitignored **SquadAnalysisArtifact** JSON to `.squadpulse/analysis/{squadId}-latest.json` on successful analyze paths; feature 002 reads it at cycle start. Config key: `communicationAssistant.analysisArtifactDir`. Not a database — runtime file only (Constitution I, XII). | high |
| 9 | Multi-turn manager approval without hosted listener | Clarify phase chose text commands on `slackTrigger` but not how subsequent `approve`/`status` messages reach the same cycle without Block Kit interactivity URLs. | **Single blocking `followups:cycle` script** with in-process **Slack thread poll loop** (`conversations.replies` every 5s, default max 60 min). Automation triggers on initial `followups` intent only; approve/status handled inside poll loop. Config keys: `communicationAssistant.cycleMaxMinutes`, `communicationAssistant.pollIntervalSeconds`. | med |
| 10 | Finding → proposal mapping ownership | Spec defines reason types and eligibility rules but not which 001 finding categories map to which reason type. | Deterministic mapper in `src/followups/map-findings-to-proposals.ts` with documented table (delivery stale/no-update → `progress-update`; unowned blocker → `blocker-clarification`; missing estimate → `estimate-reminder`; etc.). Fully fixture-testable (FR-041). | high |
| 11 | AI vs deterministic boundary for drafts and replies | Spec requires AI drafts and reply extraction with schema validation but not module boundaries. | Same two-phase pattern as 001: deterministic eligibility + confidence/urgency; AI for `draftMessage` and ambiguous reply extraction only; Zod-validated before render/send (FR-042). Prompts: `prompts/followup-draft-compose.md`, `prompts/reply-extract.md`. | high |
| 12 | Slack DM delivery and reply read APIs | Spec requires private DMs and reply monitoring but not API surface. | Extend `@slack/web-api`: `conversations.open` + `chat.postMessage` for send; `conversations.history` on DM channel for reply read on `status`. Scopes: `chat:write`, `im:write`, `im:history`, `users:read`. Reuse 001 retry policy. | high |
| 13 | Follow-up parser separation from 001 analysis parser | 001 `parse-request.ts` already claims `follow-up` as an analysis report intent — collision with communication cycle intent. | New module `src/slack/parse-followup-request.ts` with distinct intents (`startCycle`, `approve`, …). Contract: `contracts/follow-up-slack-request.schema.json`. | high |
